# Milestone 1.4 Plan: storage

## A. What the user sees at the end of 1.4

**Without a disk, or with a disk Madire doesn't recognise as its test disk** (every boot of the tests before 1.4, every QEMU boot without a disk, and `MadireOS-Test` at rest): exactly 1.3. Live mode, the same labels, the same screens; the new commands `sync` and `disk` exist (`disk` says which disks were found and why they are not used).

**With a marked virtual test disk** (a QEMU test image, or `MadireOS-Test` during the `storage` group): **Disk mode**. `/home` is the disk's ext2 filesystem; everything else (`/`, `/tmp`) stays in memory as in 1.0. At the first mount Madire creates `/home/user` with `Desktop`, `Documents`, `Downloads`, `Pictures`, `Music`, `Videos` and `Trash`. The shell starts in `/home/user`. Files under `/home` survive a restart: `sync` saves at once, an automatic save runs every 5 s, and Restart (the dialog or `reboot`) saves first. The About window's Mode row says `Disk (home is saved)`; the Restart dialog says `Files in /home are saved first.`; `version`, `df` and the console's start lines say the same. A disk with an unknown read-only feature or an error state is mounted read-only (`Disk (home read-only)`). Linux's own tools (`e2fsck`, `debugfs`) read the disk Madire wrote.

## C. The design

### C1. The RAM root today (the inventory the owner asked for, D15)

Read from the code at `5794365` (`kernel/fs/vfs.c` `build()`, `kernel/console/console.c`, the shell, the boot self-tests, the diagnostics and `user/prog/*.c`).

**What the RAM root holds at System ready, on every boot:**

| Path | Made by | Notes |
|---|---|---|
| `/` | `vfs_boot()` → `build()` (mode 0755) | the RAM filesystem's root |
| `/home` | `build()` (mode 0755) | **empty**; the shell starts here (`console.c`); `cd` with no argument goes here (`shell.c`, plan 1.0 B7) |
| `/tmp` | `build()` (mode 01777) | **empty** |

That is all: the boot log says `Filesystem: / holds home, tmp; 3 nodes, 0 data pages`.

**What does not exist in the RAM root:** no `/etc`, `/bin`, `/usr`, `/lib`, `/dev`, `/proc`, `/var`, `/boot`, `/media`, `/mnt` or `/run`. **Programs are not files:** the 28 built-in programs are images inside the kernel and the program modules are boot modules (Multiboot modules read through the physical view); `run <name>` finds them by name through `progmod`, never through the filesystem. There are no Linux-compatibility test files in the tree (the System V start-up test passes `HOME=/home` as an environment string only).

**What appears for a while and is removed again (all under `/tmp` or `/home`, all in memory):**
- the boot self-test (`fstest`): `/tmp/fstest/…` (folders `a`, `a/b`, files `f1`–`f4`, `a/b/x`, long names), every node removed before System ready (its check: no node, heap byte or page left);
- the diagnostics, on their `test=` boots only: `test=fdsys` `/tmp/fdsys-*`, `test=fdkill` `/tmp/fdkill-*` (`kernel/proc/fdtest.c`); the programs `bigio` (`/tmp/bio-*`, `/tmp/fc-*`), `dirops` (works in `/tmp`, and checks `stat /home`), `fileio`, `fileerr`, `fdops`, `fdhold` (their own names under `/tmp`); `fsmake` writes the file it is given (in the console sessions, under `/home`);
- the console sessions of the tests and the VirtualBox `files` and `shell` groups: files and folders under `/home` (`docs`, `data.txt`, …) and `/tmp`.

**What 1.4 changes there:** in **Live mode, nothing** (the three paths, their modes and the start folder stay). In **Disk mode** the ext2 filesystem is mounted on the RAM `/home` folder: the RAM `/home` stays empty and hidden under the mount, so nothing that exists today is hidden; `/` and `/tmp` are the RAM filesystem's as before. The diagnostics and test programs above never run in Disk mode except where a 1.4 check runs them on purpose.

### C2. The controller and PCI

- **PCI (new, `kernel/storage/pci*`, pure core `pci_core.c`):** configuration mechanism 1 through ports 0xCF8/0xCFC (the protected `kernel/arch/x86/io.h` used as it is); bus 0, then every PCI-to-PCI bridge's secondary bus (at most 256 buses, each visited once); multi-function devices; one log line per device found (`PCI: 00:1f.2 8086:2922 class 01.06.01`). An AHCI controller is class 01, subclass 06, interface 01. Its BAR5 (the controller's registers) is read, never resized; a 64-bit BAR above 4 GiB is refused with one line. The command register gets memory space and bus master on, and INTx off.
- **AHCI (new, `kernel/storage/ahci*`, pure core `ahci_core.c`, tested against a fake controller model):** BIOS hand-off only if the controller asks for it (CAP2.BOH); AHCI mode on (GHC.AE); for each implemented port with a device present (PxSSTS.DET = 3): its signature (PxSIG) decides; ATA disks (0x00000101) are used, ATAPI devices (0xEB140101) are listed and never sent a command; the port is stopped, its command list and received-FIS area set, errors cleared, and started; interrupts stay off (GHC.IE = 0). A port is reset (COMRESET) only after an error, at most once per error.
- **Polling** (D2): the busy bits and PxCI are read until done, bounded by `timer_ticks()` (the protected `timer.c` unchanged) and a read count; a timeout or a task-file error is an error (C5).

### C3. Memory: registers, DMA structures and the cache

- **Slot 508** (D4) gets two new areas beside `VM_TEST_PAGE` and `VM_WINDOW` (in `vm_layout.h`): `VM_DEVREG_BASE`, the controller's registers (uncached), and `VM_STORAGE_BASE`, the DMA structures and the cache. Both are mapped only on boots that find an AHCI controller. They need not be mapped before `paging_freeze_kernel_half()`: slot 508's PDPT exists from `paging_init()` (it holds the test page and the window), so the new page directories and tables are added under it later (the freeze forbids only new PML4 entries). `tests/pagetables.py` models the new areas.
- **DMA:** every page comes from `pmm_alloc_page()` through its API (the protected `pmm.c` unchanged), so every address is below 4 GiB (`PMM_ADDR_LIMIT`); no 64-bit DMA, no contiguous runs, no bounce buffers. Per port: one page for the command list (1 KiB, 1 KiB aligned) and the received-FIS area (256 bytes, 256 aligned); one page for the command table (128 aligned, up to 16 physical-region entries). Data goes straight to and from the cache's 4 KiB pages. x86 keeps DMA memory coherent with the CPU caches.
- **When:** the storage start runs **after `vfs_boot()`**, so the RAM filesystem's budget (computed from the free pages at boot) and the memory summary that the protected `tests/memory_check.py` recomputes are unchanged (confirmed in S4; if not, STOP).

### C4. The write guard (D5)

A disk may be written only if **all three** hold, checked once when the disk is attached; the result is kept by the lowest layer only (the function that builds an AHCI WRITE DMA EXT or FLUSH CACHE EXT command refuses unless the disk passed). There is no other path to a write.
1. **A virtual disk:** IDENTIFY DEVICE's model string is exactly `QEMU HARDDISK` or `VBOX HARDDISK` (AGENTS.md section 6, "virtual disks only", in code).
2. **The Madire test marker** in the first 512 bytes of the ext2 partition (ext2's first 1024 bytes are never used by ext2; `e2fsck` leaves them alone): `MADIRE-TEST-DISK`, a format version, the partition's first LBA and its sector count (equal to the partition table's), and a CRC32 over the record.
3. **The ext2 volume label** is exactly `madire-test`.

Tested by unit cases (each condition false alone) and QEMU boots: an unmarked ext2 disk, a bad marker CRC, a wrong label, a non-virtual model (`-device ide-hd,…,model=…`); each is refused and logged, and **the image's SHA-256 is identical before and after the boot**, also after a `test=diskwrite` boot that tries to write on purpose. **Relaxed** only at the installer milestone (condition 2 becomes "written by the installer after a typed confirmation"); condition 1 stays until a real-hardware milestone that the owner approves separately.

### C5. The block layer and the save (D8, with the owner's change)

- **Sectors:** 512 bytes (a disk reporting another logical sector size is refused). Requests in 4 KiB pages; partitions start at LBA 2048, so pages line up.
- **The cache:** 2 MiB (512 pages) or 1/16 of the free pages, the smaller; a fixed pool in the storage area. Clean pages are replaced least-recently-used first; a dirty page is reused only after it is written.
- **When dirty pages are written (a "save"):** `sync`; before Restart (the dialog and `reboot`); every 5 s (the automatic save; **off in every `test=` boot** except the boot option that tests it); when more than half the cache is dirty; at unmount. At most about 8 disk commands per hold of the VFS lock; a save runs in pieces.
- **The order within a save:** classes, each followed by FLUSH CACHE EXT: (1) file data; (2) bitmaps; (3) inodes and indirect blocks; (4) folders; (5) group descriptors and the superblock.
- **The owner's rule for frees (the change to D8):** a block or inode **freed since the last completed save is not reused until the save that removes its pointers has finished**; its bitmap bit is cleared **in the following save**. In memory it stays "pending free": the allocator does not hand it out, and the on-disk bitmap still says "in use".

  **Why this removes the clash.** Allocation needs "data, then bitmaps, then the pointers" (a pointer must never reach the disk before what it points to); a free needs "the pointer first, then the bitmap" (a bitmap must never say "free" while a pointer on the disk still uses the block). Inside one save the classes can only go one way. Without the rule, deleting file A and creating file B in the same save could hand A's block to B: B's data (class 1) would overwrite A's block **before** the removal of A's pointer (class 3 or 4) reached the disk, so a cut in between would leave A, whose deletion was never saved, pointing at B's data. With the rule, a block freed in this save is still in use on the disk and cannot be given to B, so every write of class 1 lands in a block that **no pointer on the disk** uses; the pointers to freed blocks disappear in this save (classes 3–4), and only the **next** save clears their bitmap bits (class 2), when no pointer on the disk can still name them. A cut anywhere leaves at worst blocks or inodes marked in use that nothing uses (leaks: allowed, section D). The same holds for inodes (a freed inode number is not reused while a folder entry on the disk may still name it). If the disk is full except for pending frees, a save runs first and the allocation is tried again; `ENOSPC` only after that.
- **Errors (D9):** no panic and no retry loop for anything about a disk. A failed or timed-out command: the port's status read, logged once, the port reset at most once, then `EIO`. After 3 errors on one disk it is marked failed and its filesystem becomes read-only (the ext2 error state written only if writing still works). Every number read from the disk is bounds-checked (block numbers, `rec_len`, depths, sizes, counts).
- **Before Restart and at a future Shut Down:** a save limited to 10 s; if it fails, Madire logs it and restarts anyway (D9).

### C6. Partitions (D10)

Read only: the MBR (the four primary entries, 0x55AA) and GPT (the protective MBR's type 0xEE, the header and its CRC32, the entry array and its CRC32, names in UTF-16LE). The ext2 partition: MBR type 0x83, or GPT type "Linux filesystem data" (`0FC63DAF-8483-4772-8E79-3D69D8477DE4`). The first partition that passes the guard is used; one disk, one partition in 1.4. Nothing is written to a partition table.

### C7. ext2 from the specification (D11, D12)

| Item | 1.4 |
|---|---|
| Revision | 0 and 1 (revision 0's fixed values: first inode 11, 128-byte inodes) |
| Block size | 1024, 2048, 4096 bytes; larger refused |
| Inode size | 128 or 256 bytes (bytes after 128 read, not used) |
| INCOMPAT | only `filetype`; any other flag → **not mounted** (Live mode, a log line) |
| RO_COMPAT | `sparse_super` and `large_file` known and written; any other → **mounted read-only** |
| COMPAT | `ext_attr`: freeing an inode lowers its attribute block's reference count (freed at 0); `resize_inode`: inode 7 and the reserved descriptor blocks never touched; `dir_index`: a folder Madire changes has its index flag cleared (allowed by the specification; Linux then reads it in order) |
| States | a read-write mount marks the volume not clean; a clean save at unmount or Restart marks it clean; the error bit set → read-only; **not clean without the error bit → read-write with a warning, after recounting the free blocks and inodes from the bitmaps (D12)** |
| Times | seconds from the CMOS clock read at boot plus the uptime (`vfs_now`), no time zone; 32-bit (until 2038); VirtualBox's clock is local time (2 h ahead of UTC on the test host) |
| Files | up to 4 GiB − 1 (`large_file`); direct, single, double and triple indirect blocks; holes |

**The order of the work:** reading first (superblock → group descriptors → inodes → direct and indirect blocks → folders → file data; S6, S8), then writing (bitmaps and allocation with pending frees → inodes → folder entries added and removed → file writes with indirect blocks → truncate and unlink → `mkdir`/`rmdir` with link counts and `..` → `rename` → the counts in the group descriptors and the superblock; S9, S10).

### C8. The VFS and the mount at `/home` (D15)

## D. Power loss: what "no data loss" means (D14)

- **A change is safe once a save has finished after it:** `sync`, the save before Restart, or the automatic save (every 5 s).
- **After a power cut, every safe file reads back exactly.** A change made after the last finished save may be lost completely or partly (a file being extended keeps its old length; an overwrite in progress can be half old, half new).
- **Never:** a safe file damaged; a folder entry pointing to a freed or garbage inode; two files sharing a block; Madire failing to boot.
- **What `e2fsck -fn` may still report after a cut** (the allowed list, fixed word for word in S9): wrong free-block and free-inode totals; blocks or inodes marked in use that nothing uses (leaks, including the pending frees of section C5); an unattached new inode; a wrong link count after a cut inside a rename; the volume not cleanly unmounted. Anything else fails the check.
- **The cut model is command-granular:** a cut falls between two disk commands; every command reaches the disk whole or not at all. **Torn sectors** (a sector half written when the power fails) **are not simulated**; real disks can tear a sector, and that is outside 1.4's evidence.
- **VirtualBox may ignore FLUSH CACHE** for VDI files: the power-loss evidence comes from QEMU and the host sweep only (risk 32).
- **How it is tested:** (a) **the host sweep** (part static, S9): the pure ext2 core and block layer run fixed operation sequences on an image file, each cut after write N **for every N**; after each cut `e2fsck -fn` must report only the allowed list and every file saved before the cut must read back exactly. **The owner's case:** after a save that holds file A, delete A and create file B with **no save in between** (without the rule of C5, B would reuse A's block), then save; cut at every N of that save: **A must read back exactly (its last saved state), or be absent only once that save has finished**, and B must never share a block with A. (b) **QEMU** (S11): `test=diskcut=N` makes the block layer stop writing after write N, log it and halt; the test script kills QEMU, runs the same checks on the image, then boots Madire again on it (the remount, the recount, the saved files). Cut tests save with an explicit `sync`; the automatic save is off in `test=` boots (C5), so every N is repeatable; one separate boot (`test=autosave`) proves the automatic save itself. Every write logs its number and its class (`blk: write N class C`, with `test=diskcut` only), so each N is read from the log of one uncut run of the same scripted sequence (the owner's delete-A-create-B sequence: save 1 writes file A; save 2 deletes A and creates B).

**Which N run where (the owner's S0 revision).** **The sharded run keeps two representative cut points** (part static, section G4):
1. **N1 = the last file-data write of save 2** (the end of class 1): B's data is on the disk, but none of B's pointers and none of A's removal. This is the point where, without C5's rule, A's block would already hold B's data; with the rule, A must read back exactly and B must be absent, with only leaks in `e2fsck`.
2. **N2 = the first folder write of save 2** (inside class 4): B's inode is written (class 3) but the folder block that removes A and adds B is not yet written. It proves the pointer order: A still reads back exactly, B's inode is at most an unattached inode (allowed), and no entry names a freed inode.

These two cover the two halves of the clash C5 removes (data before pointers; pointers before bitmap clears). **Every other N** (about 20, spread over saves 1–3, including N = 0, each class boundary, and the bitmap-clearing writes of save 3) runs in the **stress part** (G5). The host sweep (a) still covers **every N** of the same sequences in part static, so the sharded run keeps full coverage of the logic; the QEMU points prove the kernel's real path.
