## A. Question A: how workflow changes are exercised and evidenced during the milestone

**How a run is started today.** `scripts/actions-regress.ps1 -Dispatch` runs `gh workflow run regression.yml --ref main -f ref=<sha>`. `--ref main` selects the **workflow file**: GitHub runs `.github/workflows/regression.yml` as it is on `main`. The input `ref` selects the **code under test**: every job checks out that commit (`actions/checkout` with `ref: ${{ inputs.ref }}`), and the combining job checks it out too, for the test scripts.

**What therefore runs from the commit under test (the `wip/1.2` commit), and is evidence during the milestone:**
- the Makefile, `tests/qemu-tests.sh` and every `tests/qemu-part-*.sh`, the helpers (`tests/*.py`, `tests/qemu-lib.sh`), `tests/expected-checks.txt` and `tests/combine-shards.sh` (the counts, the gate, the combined report);
- whatever these print into `regression.log`, which every job uploads in its artifact.

**What runs from `main`, and does not change during the milestone:** the YAML itself: the job list, the shard matrix (`static`, `1`, `2`, `3`, `4`), the steps, the lines the "Checks" step prints (`KERNEL_MARGIN_BYTES` among them) and the artifact lists. A change to `regression.yml` on `wip/1.2` would not run until the milestone commit reaches `main`, so it could not be evidenced during the milestone. (Dispatching with `--ref wip/1.2` would run the branch's YAML, but that changes the official procedure of AGENTS.md section 5 and needs its own decision; it is not used.)

**What `main`'s YAML hard-codes (read on 2026-10-23), and what it does not:**
- **Hard-coded:** the shard matrix `part: [static, "1", "2", "3", "4"]`; the job steps (`make test-shard SHARD=<part>`, `make unit test iso` in the full job, `make test-shard SHARD=stress`); the lines its "Checks" steps print (`FINAL_SNAPSHOT_HASH_MATCH`, `UNIT_SUITES_PASS` as a count of `-> PASS` lines, `FAIL_LINES`, the symbol, helper and SSE/x87 counts, `KERNEL_END_VIRTUAL`, `KERNEL_MARGIN_BYTES`, `TWO_MIB_MARGIN_BYTES`, the hashes; the full job also greps `ALL TESTS|FAILED|MAKE EXIT|Reproducible build:|EXPECTED_CHECKS` from `regression.log`); and the artifact path lists (`regression.log`, `build/serial-*.log`, `build/*.keys.txt`, `build/*.irq1.txt`, `build/stall/`, the helper trace and logs; the full job also the ISO and `build/replay-*.txt`).
- **Not hard-coded:** no check count, total, tag, suite count or suite list. The counters per tag are in `tests/qemu-tests.sh`, the sum and the "ALL TESTS PASSED" line in `tests/combine-shards.sh`, the agreed numbers in `tests/expected-checks.txt` (with `unit-suites`), the comparison in `tests/check-counts.sh`; the unit suites are run by the Makefile; the list of parts `combine-shards.sh` expects comes from `tests/qemu-tests.sh --list-parts`. All of these come from the commit under test.

**Therefore adding `[1.2]` checks and unit suites to the existing parts works with `main`'s YAML unchanged:** the first stage that adds a counted check adds a `[1.2]` counter to `tests/qemu-tests.sh` and to `combine-shards.sh`'s sum and summary line (as 1.1 stage 1 added `[1.1]`), and the `1.2` line to `expected-checks.txt`; `combine-shards.sh` then reports the `[1.2]` count in `SHARD_COUNTS`, `EXPECTED_CHECKS=MATCH` and the "ALL TESTS PASSED (… new in 1.2)" line, and the new suites in `UNIT_SUITES_PASS` against `unit-suites`. **Two things would need a YAML change, so 1.2 avoids them:** (a) a new part: `--list-parts` would name a part the matrix never runs, and `combine-shards.sh` would fail with "no results from job shard-<part>"; (b) new evidence files outside the artifact path lists: screendumps and other files are not uploaded, so every graphics fact a check decides is printed as a line in `regression.log` (as `qmp_menu.py`'s are), and the boots' serial logs are named `serial-*.log` only when they are boot logs (derived files never are; they count in part final's report-only boot figures).

**Therefore, in 1.2:**
1. **No change to `regression.yml`** is planned. The workflow file on `main` stays the one of v1.0 (`65667b5d…`, the blob at `main:.github/workflows/regression.yml`, unchanged since `1e99f27`).
2. **The `size` reporting (stage 2)** is printed by the test scripts (part static, into `regression.log`) and repeated by `tests/combine-shards.sh`, both from the commit under test, so it is evidenced in the first run of stage 2.
3. **No new shard.** The `[1.2]` checks go into the existing parts (`static`, `1` to `4`, and `stress` for the mouse burst), placed by the measured shard durations (each stage reports every shard's seconds; the longest shard, part 4 at about 18 minutes in v1.1, is not to grow by more than about 3 minutes; the shortest, part 1, takes the larger graphics sections first).
4. **Every run report names the workflow file that ran:** the run's `headBranch` and `headSha` (from `gh run view <id> --json headBranch,headSha`) and the blob hash of `main:.github/workflows/regression.yml`. No stage claims evidence from a workflow file that is not the one that ran.
5. If a workflow change ever becomes necessary during 1.2, it is raised first and STOPs: it would be evidenced only from `main` after the milestone commit, as the 1.0 gate was.

A "before" screen is one taken while the serial log was still empty when checked just before the screendump; the kernel writes serial before it draws, so a misclassified screen can only make the check fail, never pass.

**The VirtualBox `boot` row** (`scripts/vbox-acceptance.ps1`):

| | Text (word for word) | OK when |
|---|---|---|
| Before | `boot             OK       /normal boot without the boot menu (screen never 1024 wide before System ready)/` | System ready reached and no screenshot (every 250 ms from `startvm`) 1024 wide |
| After | `boot             OK       /normal boot without the boot menu (before the first serial byte only 720x400, 640x480 or blank; no screenshot matches the menu header)/` | System ready reached; every screenshot taken while the serial log was empty is 720×400, 640×480 or blank; no screenshot equals `wallpaper.png` in the header box; every later screenshot in the kernel's logged mode |

The menu automation (`Start-Menu`, `keywindow`) keeps detecting the shown menu by the 1024 width while the serial log is empty (its rows unchanged); with the requested 1280×800 the kernel's own mode is never 1024 wide (decision 2; if the probe's fallback is 1024×768, this is raised again).

**Why the new wording is not weaker.** Both checks prove one fact: without a key, Limine's menu is never shown. Limine draws only before it hands over to the kernel, and the kernel's first instruction path writes `boot32: start` to serial before anything else, so the menu can only appear before the first serial byte. For that period the new check is **at least as strict as the old one**: it allows only the old sizes, 640×480 and 720×400, plus a blank screen (a mode set by Limine for the kernel, with nothing drawn; a menu is never one colour). It is **stricter** in two ways: the header comparison catches the menu at any resolution and at any time (the old check would miss a menu shown at, say, 800×600 if Limine fell back from 1024×768), and it requires exactly one `boot32: start` (no second boot hiding a menu). What it gives up is only the old ban on any other size after the kernel has started: a graphics screen drawn by the kernel, which is the point of 1.2 and is not Limine's menu. The blank and pixel-exact header comparisons depend on the stage 3 probe (a blank screen between mode set and first byte; the header box exact in QEMU's screendump and VirtualBox's screenshot); if either is not exact, the wording is raised again before stage 10.

- **`[0.11] normal boot: no module line on the screen (row 23 read from the VGA buffer)`** → `[0.11] normal boot: no module line on the screen (row 23 read from the console's cell grid)`: `tests/qmp_screen.py` reads the console's cell shadow at its address in `madire.elf` (`nm`) instead of `0xB8000`; the same row, the same regex, the same fact.

- **QEMU, graphics test ISOs** (paused, QMP; a new `tests/qmp_fb.py` reusing `qmp_menu.py`'s PNG decoder): the screendump's size equals the logged mode; the splash, wallpaper and desktop pixel-exact against an independent Python reference renderer, with only the clock box masked (no stored PNG hashes); the console window equal to the reference rendering of the cell grid; `test=fbpattern`'s logged CRC equal to the screendump's; the modes 800×600, 1024×768, 1280×800, 1920×1080 and one 24 bpp mode; the mouse sessions; a `display: frame N` marker (test option only) before every screendump.
- **QEMU, `-kernel`:** `Display: VGA text 80x25 (no framebuffer)`; `test=mouse`.
- **Stress part:** the mouse burst (1000 packets, no loss).
- **VirtualBox:** the `graphics` group (screenshots against the reference renderer, the clock masked; the mouse if the probe shows injection works, else a manual check by the owner).

`tests/expected-checks.txt` gets its `1.2` line in the first stage that adds a counted check, and is updated in every stage that adds or changes checks.

## F. Risks

1. **Limine's Multiboot 1 behaviour** (honouring the video request, per-entry `textmode`) is not yet verified: stage 3 comes first; fallbacks are a kernel-side mode set (emulators only) or bringing the Limine protocol forward, each a new decision.
2. **TCG drawing speed** and boot time limits: dirty rectangles only; measured at the checkpoint (section C).
3. **The screen rule:** thread 0's redraws can delay keys; redraw cost is bounded and measured.
4. **Page-table, mapped-page and free-page figures** change on framebuffer boots (slot 506, the back buffer).
5. **Kernel growth:** the estimates of 1.0 were half the measured growth; `size` is reported from stage 2, and decision 13's trigger (below 524,288 bytes) stops the work for a gate stage.
6. **VirtualBox mouse injection** may not exist or may not reach the PS/2 aux device with `usbtablet` (decision 11 after the probe).
7. **OFL renaming:** the converted font is a Modified Version; it is never called "Terminus Font" in the user interface.
8. **The mockup is AI-generated** (Microsoft Designer): used as a local reference only; never in the repository, never shipped, no pixels copied.
9. **Added serial lines** could fall inside an `expect_lines` window or a console session: checked in every stage.
10. **Real hardware:** the framebuffer mapped write-back (PAT write-combining later); untested on real hardware (out of scope).
11. **Host memory** for VirtualBox runs (AGENTS.md section 6), and for the view VM if it is approved.
12. **1280×800 may be missing** from VirtualBox's BIOS VBE list (decision 2): the probe reports the fallback before stage 5.

## G. Deliberately left for 1.3 and later

Storage (a disk driver and a persistent filesystem; Madire's own or ext2), the installer, ACPI (shutdown, poweroff), APIC/IOAPIC, SMP, UEFI with the Limine protocol and GOP, USB input, smooth fonts (stb_truetype with Inter or Noto), the icon set, Files, Settings, Web, sound, Shut Down, translucency and blur, the login screen (secret input), a user-space compositor, LVGL, run-time mode changes and virtio-gpu, more than one monitor, notifications, the tray and widgets, app search, keyboard layouts, desktop icons and the top bar of the mockup. If the checkpoint decides so, the desktop (9a, 9b) also.

## H. Actions runs

Every code stage: one sharded run on the stage's commit (`scripts/actions-regress.ps1 -Dispatch`, then `-Collect`), plus the stress part where the table says so; a full run at stage 10 and stage 12 (the full run also uploads the ISO for VirtualBox). No run is started while a decision of the owner is open (AGENTS.md section 5). Every run report gives the commit, the workflow file that ran (section A) and the results by tag, with the unit suites, `make repro`, the symbol and SSE checks, `size` (from stage 2) and the protected-file diff.
