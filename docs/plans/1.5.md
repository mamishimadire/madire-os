## C. The design

### C1. The per-disk I/O lock (decision 1)

**Today (1.4):** a save runs in pieces of at most 8 disk commands (`ext2_d_piece`), each under the VFS lock; VFS holders run with preemption off and the AHCI driver polls, so during a piece nothing else runs (not the desktop, the pointer, the clock or a program), up to 10 s for a real FLUSH.

**Why the order matters:** on one CPU, a VFS holder (preemption off, never yields) that needs a disk read while a preempted save owns the disk would wait for ever. So the disk lock comes **first**.

**The design:**
- **In Disk mode** `fd_vfs_acquire()` takes the disk lock, then the VFS lock; `fd_vfs_release()` gives back both. Every existing path that releases the VFS lock to wait (a busy mark, the `EXT2_EAGAIN` retry `ext2_disk_retry`) therefore releases the disk lock too.
- **The disk lock** is a FIFO ticket lock (the ticket logic of `klock_core`, a new preemptible kind): its holder keeps preemption on and may yield while it waits for the hardware; a waiter yields until its ticket is served.
- **A save piece** (the automatic save, `sync`, `EXT2_EAGAIN` retries, the save before Restart and Shut down) holds **only the disk lock**: the save store is frozen while a save is in progress (`blk_sv_put` already refuses), and no filesystem call can run in Disk mode without the disk lock. The AHCI wait loop yields between status reads while its caller holds the disk lock.
- **Live mode never takes the disk lock** (no disk mounted): nothing changes there.
- **Limits (documented):** in Disk mode a file call waits while a save piece runs, also on `/tmp`; a disk read after a cache miss is still sent inside a VFS hold (one bounded command; removing it needs interrupt-driven AHCI, later); thread 0 itself waiting (for example the Files app reading a folder during a long FLUSH) pauses the desktop for that piece.

**The rules (each an always-on self-check that panics with its name, as the 1.0 lock checks do):**
- **L1** the disk lock is taken before the VFS lock, never while the VFS lock is held;
- **L2** disk-lock holders keep preemption on and may yield; VFS holders are unchanged (preemption off, never yield);
- **L3** one owner; the owner never takes it again;
- **L4** never taken from an interrupt handler;
- **L5** the AHCI port and the read cache are touched only by the disk lock's owner;
- **L6** never taken in Live mode.

**How the tests prove it:** the lock core's unit suite (tickets, owner, the order check); `test=blkslow=<ms>` (after a write or FLUSH has finished, the driver waits `<ms>` longer by yielding: a slow disk): thread 0's idle loop and a ticker thread keep running during a 500 ms FLUSH (counted), and after System ready **no write or FLUSH command is ever sent while the VFS lock is held** (a counter that must be 0; counted); `test=diskcontend`: a program writes under `/home` while saves run, both finish, `e2fsck -fn` clean; two selfcheck boots (`test=selfcheckdisklock` breaks L1, `test=selfcheckdiskrelock` breaks L3), each panicking with its message. The boot-time mount no longer holds the VFS lock across save 0, so its 1.4 exemption goes (a CHANGED CHECK, H2 item 3).

### C2. The ext2 tables in pages allocated at the mount (decision 2)

Today `ext2_d_w` (the read core and its buffers, about 29 KiB; the pending table of 4,096 entries; the fresh table; 9 block buffers) and `ext2_d_ents` (2,048 × 12 bytes) are about 139 KiB of `.bss` on every boot.

- **Two allocations in slot 508**, next to the save store (new areas in `vm_layout.h`, mapped only when a disk is mounted): first the read core's pages, then the write tables' pages. The pure cores take pointers to their tables instead of built-in arrays (an init call with the buffers; the unit suites give static buffers).
- **The fallback:** the read core's pages missing → the disk is not mounted (Live mode; `ext2: too little memory for the read core: not mounted (Live mode)`); the write tables' pages missing → mounted read-only (`ext2: too little memory for the write tables: mounted read-only`; the existing read-only wordings of 1.4 C10 on the screen).
- **Effects:** Live mode costs nothing; the kernel's end moves down by about 139 KiB but stays above 2 MiB (today `0x2B4000`), so the page-table count is unchanged; every boot's free and mapped page figures change (the protected `tests/memory_check.py` recomputes them; S5 searches every check for a pinned figure and lists any as a CHANGED CHECK); the margin grows by about 142 KiB.
- **Tested by:** the unit suites with the new init; `test=diskwmem` (the write tables' allocation fails on purpose: read-only, the image's hash unchanged) and `test=diskrmem` (the read core's allocation fails: Live mode); a `size` check that `madire.elf`'s `.bss` fell by at least 130,000 bytes (counted).
- **First:** a full search for every caller and initializer of the changed structures (1.4 stage 7's lesson) before the commit.

### C3. Shut down (decisions 3, 4, 5; addition b)

**The implementation licence (the owner, S0 review; risk 65):** the UEFI Forum's specifications may be downloaded and read only; a licence to implement them comes with the free UEFI Adopter Membership Agreement (references.md, the ACPI specification's row). **The ACPI power-off code below (the RSDP, RSDT/XSDT, FADT and DSDT parsing, the `_S5_` decoding, the PM1 writes) is written only after the owner confirms the signed agreement.** If it is not confirmed when S6 is due, the owner chooses at S6 between (i) waiting, or (ii) S6 shipping the power dialog, `poweroff`, the save, FLUSH and mark-clean path and the "safe to turn off" screen only (every power-off then ends on that screen, with the reason `power-off is not available yet`), with the ACPI power-off moved to a later stage of its own.

**The path (no AML interpreter):**
1. Find the RSDP in the EBDA's first KiB and in `0xE0000`–`0xFFFFF` (the low 1 MiB is already mapped by the physical view).
2. Read the RSDT (or the XSDT if the RSDP revision is 2 or more), the FADT and the DSDT through the physical-access window, one page at a time.
3. Find `_S5_` in the DSDT's AML bytes and decode its package's first two values (SLP_TYPa, SLP_TYPb).
4. If PM1a_CNT's SCI_EN is clear and the FADT gives SMI_CMD and ACPI_ENABLE: write ACPI_ENABLE to SMI_CMD and wait for SCI_EN (bounded: 1 s by the timer).
5. **Read-modify-write:** read PM1a_CNT, clear only the SLP_TYP field (bits 10–12), set SLP_TYPa there and SLP_EN (bit 13), keep every other bit as read (SCI_EN included), and write it back; the same for PM1b_CNT with SLP_TYPb if it exists.
6. Still running 2 s later, or any step failed: **the fallback screen** (full screen, on the framebuffer or in VGA text): `It is now safe to turn off the computer.` and `Madire OS could not power off by itself (<reason>).`, then halt with interrupts off.

**The tables are untrusted firmware data (addition b):** each table's signature, length and checksum are checked (the RSDP's 20-byte checksum and, from revision 2, its extended checksum; the RSDT/XSDT, FADT and DSDT whole-table checksums); every read stays inside the table's stated length (and inside the RSDT's entry count); the `_S5_` search reads only inside the DSDT's stated length, and the package decoder bounds every length byte and value prefix it reads (`PkgLength` of 1-4 bytes, `BytePrefix`, `Zero`, `One`); a table longer than a fixed limit (1 MiB for the DSDT, 64 KiB for the others) is refused; any failure leads to the fallback screen with its reason, never to a fault. The tables are read when the power-off is chosen, not at boot (no boot change), and logged in one `ACPI:` line.

**What each emulator does:** QEMU (its PIIX4 power management) powers off and sends the QMP event `SHUTDOWN` (`"reason": "guest-shutdown"`); QEMU then exits. VirtualBox: the VM state becomes `poweroff` by itself (`VMState="poweroff"`); its DSDT must hold `_S5`, which S6's owner-run probe proves early.

**Shut down during a save (addition c), with no gap after the last save:** the power-off thread (thread 0) first stops the automatic save (no new automatic save starts), then takes the disk lock (it waits for the current save piece to end, yielding) and **keeps it** through the final full save, the mark-clean, the superblock's save, the FLUSH and the S5 write: the lock is never given back before the power-off, nor before the fallback screen's halt with interrupts off, so no other thread can change or write anything after the last save. The saves inside this hold call the save pieces as the lock's owner (never taking the lock again, L3). **Live mode skips the save** (no disk lock, L6). **Restart (reviewed in S0, no change):** `ext2_disk_restart_save()` (`kernel/fs/ext2_disk.c`) marks the volume closed (`ext2_d_vfs.closed`, checked in `kernel/fs/ext2_vfs.c`, so no change reaches the disk after it), then saves in pieces and gives the lock back between them; the automatic save may run a piece in between but finds the same frozen save or nothing dirty; then `reset_machine()` starts with `cli`. No data gap was found; Restart's path is unchanged (it takes the disk lock per piece from S4 on, like every save). **The time limit (D9, as Restart):** the whole save is limited to 10 s from the click; if it fails or does not finish, Madire logs `ext2: save before power-off: not finished (<reason> after <n> ms): powering off anyway (D9)` and powers off. A read-only volume saves nothing (`ext2: save before power-off: nothing saved (/home is read-only: <why>)`).

**The interface:** the M menu row **Power...** opens the power dialog (title `Power`, the line `Shut down or restart Madire OS?`, the second line from 1.4 C10 unchanged per mode, the buttons **Shut down**, **Restart**, **Cancel**; Esc cancels); Restart behaves exactly as 1.4's Restart dialog did. **`poweroff`** (SYSTEM; help section `system`; purpose `Power off the computer (asks first)`) asks `Power off now? Type 'yes' to confirm:` at `yes/no> `; anything but `yes` prints `Power off cancelled.`; `-y` skips the question; in Disk mode it prints `Saving files... done.` (as `reboot`). MOCS v0.13.

**Tested by:** an `acpi_core` unit suite on built tables (good tables; a bad checksum, a bad length, a truncated `_S5_` package, `_S5_` at the DSDT's end, an RSDT entry pointing outside, an XSDT, no PM1b: each a named case leading to "fallback" with its reason; and `acpi_pm1_rmw_keeps_bits`: from PM1 values with SCI_EN and every other bit set or clear, the value written differs from the value read only in bits 10–13); QEMU boots: `poweroff -y` in Live mode (QEMU exits with the guest-shutdown event within 5 s; counted), in Disk mode (the save, then the event; `e2fsck -fn` clean; the volume marked clean; counted), with `-machine acpi=off` (the fallback screen's two lines on serial and in the cell grid; QEMU still running; counted); the power dialog on the desktop (part 5, the scenes against `tests/desktop_ref.py`).

### C6. The Trash (decisions 7, 8; the owner's answer 1; addition a)

- **Where:** `/home/user/.local/share/Trash` (the XDG default of `$XDG_DATA_HOME/Trash`), with `files/` and `info/`, made when first needed (Disk mode: on the disk; Live mode: in memory). **1.4's visible `/home/user/Trash`:** at a read-write mount, if it exists and is an empty folder it is removed (logged: `home: the empty /home/user/Trash of 1.4 removed (the Trash is now /home/user/.local/share/Trash)`); if it holds anything it stays as a normal folder (logged). - **Move to Trash (the specification):** `info/<name>.trashinfo` is created first, exclusively (`O_EXCL`; if the name is taken, `<name>.2`, `<name>.3`, ... up to 999, then `Can't move '<name>' to the Trash: too many items with this name.`), then the item is renamed into `files/<name>`; if the rename fails, the info file is removed. The info file: `[Trash Info]`, `Path=` (the absolute original path, percent-encoded per RFC 2396 section 2), `DeletionDate=YYYY-MM-DDThh:mm:ss` (local time, as the specification says; the RTC's time). The optional `directorysizes` cache is not written.
- **What cannot go to the Trash** (decision 8): an item on another filesystem than the Trash (Disk mode: anything outside `/home`, such as `/tmp`): `Delete '<name>' permanently? It can't go to the Trash.` with **Delete** and **Cancel**.
- **The Trash view:** **Restore all** and **Empty Trash** at the top; **Restore** on the selected item (the owner's answer 1); each row shows the name, the original folder and the deletion date. **Restore:** rename back to `Path`; a missing original folder is made again; a name already there: `'<name>' already exists in <folder>.` with **Keep both** (the restored item gets ` (restored)`, then ` (restored 2)`, ...) and **Cancel**; then the info file is removed. **Empty Trash** asks `Empty the Trash? <n> items will be deleted permanently.` (**Empty Trash**, **Cancel**), then deletes in steps (C5's limits).
- **`.trashinfo` is untrusted input (addition a).** The parser (pure, `trash_core`) is fully bounded: the file at most 8 KiB (larger: refused unread); lines at most 4,096 + 64 bytes; the first non-empty line exactly `[Trash Info]`; the first `Path=` and the first `DeletionDate=` count (later repeats ignored, as the specification says); other lines ignored. **`Path` is accepted only if, after strict percent-decoding:** every `%` is followed by exactly two hexadecimal digits; it decodes to no NUL byte and no `/` escaped as `%2F`; it is absolute; it lies under `/home/user/` (the home Trash's only allowed base; the Trash's own mount is `/home`); it has no empty component (`//`), no `.` or `..` component, no trailing `/`; each component is at most 255 bytes and the whole path at most 4,096 bytes; and it does not name the Trash itself or anything inside it. A bad `DeletionDate` (not exactly `YYYY-MM-DDThh:mm:ss` with valid ranges) shows `(unknown date)` but does not block Restore. An item whose info file is missing or refused shows `(unknown original location)` and **cannot be restored** (it can still be deleted by Empty Trash); an info file without its item is ignored and removed by Empty Trash. **Named unit cases in the `trash_core` suite:** `ti_ok_simple`, `ti_ok_encoded_space`, `ti_ok_utf8_bytes`, `ti_bad_header`, `ti_no_path`, `ti_relative_path`, `ti_outside_home`, `ti_dotdot_component`, `ti_dot_component`, `ti_empty_component`, `ti_trailing_slash`, `ti_escape_short`, `ti_escape_nonhex`, `ti_escape_nul`, `ti_escape_slash`, `ti_component_too_long`, `ti_path_too_long`, `ti_line_too_long`, `ti_file_too_large`, `ti_inside_trash`, `ti_duplicate_keys_first_wins`, `ti_bad_date_restorable`, `ti_encode_roundtrip`, `ti_restore_through_symlink`, `ti_restore_parent_is_link` (rule SL, C6c).

### C6c. Symbolic links: rule SL (security; risk 66)

**Today (read in S0, no change):** Madire's VFS never follows a symbolic link. `struct vnode` has two types only (`VNODE_FILE`, `VNODE_DIR`; `kernel/fs/vfs_core.h`); the ext2 adapter's `ext2_vn_fill()` (`kernel/fs/ext2_vfs.c`) makes every inode that is not a folder a `VNODE_FILE`, symbolic links included, and drops the type bits from the mode (`in->mode & 07777`); so a link in the middle of a path answers `ENOTDIR` and a link at the end is opened as a file whose contents are the target text: `ext2_read()` (`kernel/fs/ext2_core.c`) reads a fast link's target from `i_block` (`ext2_fast_link()`) and a slow link's from its data block. Writing to or truncating a link is refused (`EINVAL`: `ext2_write_pwrite()` and `ext2_write_truncate()` in `kernel/fs/ext2_write.c` accept regular files only); removing a link's last name frees its data block only for a slow link (`ext2_w_name_gone()`: a fast link's `i_block` holds text, not block numbers). Madire cannot create links (no `symlink` system call; the RAM filesystem has none), so a link can only come from a disk written elsewhere, for example a planted one.

**The rule SL (1.5):** Restore, re-creating a missing original folder, recursive Copy and Paste, a move across filesystems, Delete permanently and Empty Trash **never follow a symbolic link**:
- every existing component of a target path must be a real folder (an lstat-style check of each component's own type, not its target's); otherwise the action is refused with its listed message (C6b) and nothing changes;
- a link itself is deleted, renamed (moved within a filesystem, or into the Trash) as a link, never its target; a recursive delete or Empty Trash removes a link as an entry and never descends through it;
- **copying a link** (Copy and Paste, a move across filesystems) is refused in 1.5 (`Can't copy '<name>': it is a link, and links can't be copied yet.`), because Madire cannot create a link; the link is left where it is;
- **Files** shows a link as an item (its own icon) and opens it as the info panel with the type `Link`; the Text Viewer never opens a link.
- **The adapter's change (S12):** the ext2 adapter marks a link node (a node flag or a third vnode type; `struct vnode` stays 72 bytes, its compile-time check unchanged), so the Files and Trash code can tell a link from a file; path lookup keeps answering `ENOTDIR` through a link. It lands in **S12**, the stage that brings the Text Viewer and the info panel (and already touches `kernel/fs/*`), so both treat links correctly from their first stage; unit case `ext2_vfs_link_marked` (a fast and a slow link marked; a file and a folder not; lookup through a link still `ENOTDIR`).

**Unit cases:** in `trash_core` `ti_restore_through_symlink` (a `Path` whose existing folder component is a link: refused, nothing renamed) and `ti_restore_parent_is_link` (re-creating a missing folder under a link: refused); in `files_core` `files_copy_symlink_not_followed`, `files_delete_symlink_not_followed` (the link removed, the target and its folder unchanged), `files_empty_trash_symlink_not_followed`, `files_paste_target_through_symlink` (a target folder reached through a link: refused) and `files_move_symlink_as_link` (a rename within a filesystem keeps the link). **A QEMU check (S13):** a Disk-mode test image with a fast and a slow link (one to a folder outside `/home/user`, made by `debugfs` on the host) put in the Trash, restored and deleted: `debugfs` shows the targets unchanged every time.

## L. Risks

Risk 13 stays open. The numbering continues from 1.4's 43:

44. **A disk-lock deadlock** (the order, busy marks, the retry save). Rules L1–L6 as always-on self-checks; the busy-mark and retry paths release both locks; `diskcontend` and `blkslow` boots; the selfcheck boots.
45. **Preemptible save holders change test timing** (new races between saves and sessions). The retake rules of 1.4; the stress part repeats 1.4's churn and cut points.
46. **The ext2 cores' structure change breaks unit suites.** A full search for every caller and initializer first (1.4 stage 7's lesson); the Kali trial.
47. **The ACPI tables differ** (VirtualBox, QEMU, real hardware; an `_S5_` written in a form the shortcut does not decode). The fallback screen; S6's owner-run probe; real hardware unproven.
48. **Power-off before the data is on the disk.** The final save's FLUSH before S5; the S17 Kali check after the VM powered itself off; VirtualBox may ignore FLUSH (risk 32).
49. **Enabling ACPI mode hangs on real hardware** (SMM). A bounded wait (1 s); only when SCI_EN is clear.
50. **`MadireOS-Test`'s USB tablet keeps wheel data from the PS/2 mouse.** S7's owner-run probe; the 3-byte path unchanged; if `dz` does not arrive, the VirtualBox wheel rows report only (an owner decision then).
51. **4-byte packets lose their framing.** The re-sync rule; unit cases at every offset.
52. **Screen-sized surfaces exceed the quarter share.** The drawn-on-exposure fallback; `desktopnosurface` boots.
53. **The changed checks are more than listed** (every scene with a window changes in S8). A full search in each stage; the list shown before and after; STOP.
54. **The time budget is overrun.** H3's rule; S2's moves; S9b cut first.
55. **Trash name, encoding or cross-filesystem bugs.** `trash_core`'s unit cases; `debugfs` checks of `files/` and `info/` in QEMU and on Kali.
56. **Recursive copy or delete holds locks too long, or meets risk 43's node table.** Steps with bounded holds; the depth limit 64; Files keeps no nodes open; `ENOMEM` shown, nothing half-done.
57. **Names outside printable ASCII.** Shown as `?`; typed names ASCII only; documented.
58. **The text field needs the protected `lineedit.c` changed.** It uses the public `struct lineedit` only; if not possible: STOP and raise.
59. **The Live home folders leak into existing checks.** Made only at the desktop's start (default path) or with `livehome`; the boot inventory and the start folder unchanged; S12's full search.
60. **Thread 0 waits for a slow FLUSH** (the desktop pauses for one save piece when Files reads during it). Measured in `blkslow` (report only); documented.
61. **The ISO fix disturbs booting.** Every boot check unchanged; two builds compared byte for byte in every run.
62. **The phase lines fall inside `expect_lines` windows** (as risk 33). Before System ready only; checked every stage.
63. **A malicious or corrupt `.trashinfo`** (a crafted `Path` restoring outside the home folder, a `..` walk, bad escapes, huge lines). The bounded parser of C6: strict percent-decoding, absolute paths under `/home/user/` only, no `.`/`..`/empty components, no escaped `/` or NUL, length limits; a refused file blocks Restore only (the item shows `(unknown original location)`); the named `ti_*` unit cases.
64. **Malformed ACPI tables** (bad signatures, lengths or checksums; pointers outside; a truncated `_S5_` package). Signature, length and checksum checked for the RSDP, RSDT/XSDT, FADT and DSDT; reads only inside stated lengths and the `_S5_` search only inside the DSDT; size limits; any failure → the fallback screen with its reason, never a fault; the named `acpi_core` unit cases.
65. **The ACPI implementation licence is not yet in place** (the UEFI Forum's specifications are for reading only; a licence to implement comes with the free UEFI Adopter Membership Agreement). S6's ACPI power-off code is written only after the owner confirms the signed agreement; S0–S5 are not affected; if it is not confirmed when S6 is due, the owner chooses between waiting and option (ii) of C3 (the power dialog, `poweroff`, the save, FLUSH and mark-clean path and the "safe to turn off" screen only; the ACPI power-off in a later stage of its own). **Mitigation since S6 (the owner's decision, 2026-11-13; the note at the top):** the owner signed the agreement and sent it to `admin@uefi.org` on 2026-11-13 (as an individual), which the owner judged to meet uefi.org's wording that the licence is obtained by executing and returning it; S6 implements the ACPI power-off in full. The gate is now the release: S18b waits for the Forum's confirmation; without it by S18, the owner sends a follow-up and decides then; on a refusal, only the ACPI part (the `acpi*` files, the `io.h` change, their checks and the power probe) is removed before the release, and every power-off ends on the "safe to turn off" screen.
66. **A planted symbolic link redirects a Trash or Files operation outside `/home/user`** (a link in a restore path, a paste target or a folder being deleted, on a disk written elsewhere). Rule SL (C6c): links are never followed; every existing component of a target path must be a real folder (lstat-style), otherwise the action is refused with its message; a link is deleted or moved as a link, never its target, and never copied in 1.5; the named `ti_*` and `files_*` link cases; S13's QEMU check with fast and slow links.
