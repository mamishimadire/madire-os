# Milestone 1.3 Plan: the desktop

## A. What the user sees at the end of 1.3

No key during Limine's 2 s: the splash as in 1.2 while booting; at System ready a cut to **the desktop**: the procedural wallpaper with the logo, the wordmark and the tagline, the hint "Press any key to open the console" below them, a **taskbar** with the **M button** at the left and a **clock** (`HH:MM`) at the right, and the **pointer**, drawn from the first mouse movement on. **Any key** opens the **Console window** (that key is not typed, as since 0.5); the console runs the existing shell unchanged, in an 80×25 grid at the screen's scale. A click on the M button, or the **Windows key** (also with a window focused), opens the **M menu** (About, Console, Restart); a right-click on the desktop opens a small menu (Open Console, About Madire OS). **About** opens the About window; **Restart** asks first in a dialog (Cancel, Restart). Windows can be dragged by their title bar, raised and focused by a click, and closed; closing the Console window hides it and the shell session goes on. If the checkpoint approves it, a **Calculator** window too. Esc during the splash, the boot option `verbose`, a FAILED line, a panic, and every boot with a `test=` option behave as in 1.2 (the full-screen console; the crash screen full-screen). A key during Limine's 2 s shows the boot menu as in 1.1, and the Diagnostics entries boot in text mode as today.

## B. Decisions (the design report of 2026-10-24; the owner's outcomes)

1. **Architecture: APPROVED.** The desktop runs in the kernel, drawn by thread 0 (1.2's decision 5, the hybrid), with Madire's own pure, host-tested toolkit. A user-space compositor waits for the Linux-compatibility milestone; it would need `mmap`/`munmap`/`brk`, shared memory between address spaces (`memfd_create` or a tmpfs file with `MAP_SHARED`, reference-counted frames), `poll`/`ppoll` or `epoll`, AF_UNIX sockets with `sendmsg`/`recvmsg` and `SCM_RIGHTS` (or `pipe2`), `ioctl` for an input device and for fbdev or DRM dumb buffers, `fcntl(O_NONBLOCK)`, `clock_gettime` and `futex`, all deferred today (architecture.md, *Deferred*), and `munmap` brings AGENTS.md section 10's atomic check-then-copy rule. The toolkit stays free of kernel dependencies so that it can move to user space later.
2. **The back buffer: APPROVED.** From System ready on (desktop boots only), a compositor on thread 0 owns the back buffer and is the only code that copies to the framebuffer. The splash owns it until then, as in 1.2. The crash screen stays 1.2's full-screen grid drawn on the framebuffer (section C3). The screen rule (only thread 0 draws) is unchanged.
3. **Window drawing: APPROVED, retained surfaces.** Each window draws into its own surface; the compositor composes damaged rectangles from them.
4. **The background cache: APPROVED.** The whole background (the wallpaper with the logo, the wordmark, the tagline and the hint) is cached, under the 1/4 share (drawn again once, without the hint, when the Console window is first opened); when it does not fit, the background is recomputed per damaged rectangle; a test option forces that path (section C4).
5. **The Console window: APPROVED.** A fixed 80×25 grid at the screen's scale; closing hides it and the session goes on; no resizing or maximising in 1.3.
6. **When the desktop shows: APPROVED.** Only on the default path (no `test=` option, or one of the `test=desktop…` options); Esc, `verbose`, FAILED and every other `test=` boot keep 1.2's full-screen console.
7. **At System ready: APPROVED, with the hint.** Any key opens the Console window and is not typed; a muted hint line below the tagline until the first open.
8. **Scope: APPROVED** (section E): in: the wallpaper and logo, the taskbar with the M button and the clock, the pointer always on (on the desktop), the M menu (About, Console, Restart), the Console and About windows, the right-click desktop menu (Open Console, About Madire OS); the Calculator after the checkpoint; waits: minimise, taskbar window buttons, desktop icons, the top bar, Settings, Files, Web, Shut Down, several consoles, resizing and maximising.
9. **Restart asks first: APPROVED.** A dialog with Cancel and Restart (Cancel focused), as `reboot` asks; Restart takes the existing reset path (`kernel/arch/x86/reset.c`).
10. **Window chrome: APPROVED, close only.** Minimise waits for taskbar window buttons.
11. **The clock: APPROVED.** 24-hour `HH:MM` from the CMOS clock, updated when the minute changes, no date, no time-zone label.
12. **Pixel checks: APPROVED.** Exact in QEMU, the clock drawn by the reference from the string the kernel logs; the clock's box masked in VirtualBox (section G).
13. **The VirtualBox `desktop` group via `IMouse.PutMouseEvent`, no VM change: CONDITIONAL.** The evidence, how the events reach the guest, and what is not yet proven are in section D; the missing part gets a report-only proof step in stage 3. The VM is not changed.
14. **Shards: APPROVED.** No change to `regression.yml` and no new shard; section timings first, then whole sections moved between parts, each move proven by amendment A3 (section G); every shard at or below about 1,100 s.
15. **The Calculator: APPROVED as a go/no-go at the checkpoint.** A built-in toolkit app with integer decimal maths (a signed 64-bit value scaled by 10^6; an error on overflow), decided at the checkpoint (section E, CP).
16. **Console keys: APPROVED.** Ctrl+L, Ctrl+A, Ctrl+E, Ctrl+K, Ctrl+U and Ctrl+W in stage 7; Ctrl+D deferred until `exit` exists.
17. **Carried items: APPROVED** (section J): AGENTS.md section 4 at stage 0; a 30-boot risk 13 sample at stage 9; `time` alone closed with a note (in stage 10, A4); the early-panic gaps deferred; the size gate unchanged.
18. **Terminus stays the interface font in 1.3: APPROVED.** Smooth fonts later.
19. **Design Guide v0.2 before any drawing code: APPROVED.** Written in stage 0 ([design-guide.md](../design/design-guide.md), sections 2, 5 and 8–12), with the contrast table the owner asked for (section 12: every text and icon colour against each background it appears on, its ratio and its rule; stage 4 checks against it). Computing it changed four draft choices before adoption: the M inside controls stays `accent` (the gradient's deep end is below 3:1), a selected menu row and the open M button carry a 2 dp `accent` bar (the `surface.active` fills alone are below 3:1), a pressed Calculator key fills with `accent`, and no text may lie over a curve's core.
20. **Opening the M menu by keyboard: INCLUDE in stage 5 (the owner, stage 0).** The Windows key (already decoded as `KEY_LGUI`/`KEY_RGUI` in `drivers/keyboard/scancode.h` and doing nothing today; no protected file changes, the desktop reads the existing key code) toggles the M menu: it **opens it with its first row (About) selected and marked by the focus ring**; the Windows key or Esc closes it; Up, Down and Enter work as in every menu. **With a window focused, the Windows key still opens the M menu and is not passed to the window** (the Console window never sees it). While the Restart dialog is open the dialog keeps every key (C5), so the Windows key does nothing then. The design report's recommendation was DEFER.

## C. The design

### C1. Who owns the back buffer

| Phase | Owner of the back buffer | Who copies to the framebuffer |
|---|---|---|
| Boot, splash (1.2) | `splash.c` | `splash.c`, `fbcon.c` (as in 1.2) |
| From System ready, desktop boots | the compositor (`kernel/display/compositor.c`, new) | the compositor only, one damaged rectangle at a time |
| Esc, `verbose`, FAILED, every other `test=` boot | `fbcon.c` (full-screen, as in 1.2) | `fbcon.c` |
| A panic, any phase | the crash screen: `fbcon.c` full-screen, drawn on the framebuffer (1.2's direct path) | `fbcon.c` |

The compositor keeps a fixed list of damaged rectangles (32; when it is full, the list becomes its bounding rectangle). Once per pass of the idle loop (after `pointer_poll()`), for each damaged rectangle it copies, in order: the cached background (or recomputes it, C4), the visible windows from back to front (their surfaces, or their exposure painting, A1), the taskbar, then any open menu or dialog; then the rectangle goes to the framebuffer through the pointer's existing hide/show hooks (`pointer_hide_over`, `pointer_unhide`), so the pointer stays a save-under overlay on the framebuffer as in 1.2.

### C2. fbcon in a window

`fbcon_draw_cell()` already takes a surface and a layout. The pure part gains `fbcon_layout_at(scale, …)` (the grid at 0,0 at a given scale; today the scale comes from the surface's height, which a window's would get wrong); `fbcon.c`'s `back` becomes the Console window's surface and `present_cell` reports damage to the compositor instead of copying to the framebuffer. The grid stays 80×25 at the screen's scale and always fits above the taskbar (800×600: a 642×433 window in the 560 px above it; 2560×1440 at 200 %: 1280×800 plus a 64 px title bar). The console keeps writing the VGA driver's `vga_shadow` exactly as today.

### C3. The crash screen

Unchanged from 1.2: on a panic, `fbcon` draws the full-screen grid on the framebuffer (the direct path of the early crash screen), whatever the compositor was doing; the pointer is not drawn on it. The `[1.2]` crash-screen checks are unchanged.

### C4. Memory: the background cache and the window surfaces (amendment A1)

Both live in **slot 506**, in a third area after the framebuffer's and the back buffer's (each area up to 1 GiB, `kernel/memory/vm_layout.h`), on frames from the page allocator; the kernel heap (16 MiB at most) is too small. **Everything is planned once, when the desktop starts,** in a fixed order: the cache, then the Console window's surface, then About's, then the Calculator's (if any), each in the framebuffer's format. Nothing is freed while the desktop runs (closing a window keeps its surface), so the page-table, mapped-page and free-page figures of a desktop boot are fixed and `tests/pagetables.py` can model them.

| Mode | Back buffer (1.2) | Cache | Console | About | Calculator | Extra in total |
|---|---|---|---|---|---|---|
| 1024×768×32 (100 %) | 768 pages | 768 pages (3,145,728 bytes) | about 290 pages | about 150 pages | about 90 pages | about 1,300 pages (5.1 MiB) |
| 2560×1440×32 (200 %) | 3,600 pages | 3,600 pages (14,745,600 bytes) | about 1,130 pages | about 590 pages | about 360 pages | about 5,700 pages (22 MiB) |

At 24 bpp each figure is three quarters. **The share rule (`FBPLAN_SHARE`, 1.2):** the back buffer and slot 506's tables already take at most a quarter of the free pages; in 1.3 the display's pages in all (the back buffer, the cache, the window surfaces and their page tables) stay at or below a quarter of the free pages counted when the desktop starts. Each item is mapped only if it still fits after the items before it.

- **The cache does not fit:** the background is recomputed for each damaged rectangle (the same rule, the same pixels; the wallpaper costs about 0.18 µs per pixel on Actions' TCG). Logged: `Desktop: background not cached (N pages over the share): drawn per damaged rectangle`.
- **A window's surface does not fit (A1): fallback chosen, "redraw on exposure".** The window has no surface. **During composition**, when a damaged rectangle covers part of it, the compositor has the window redraw that part **into the compositor's back buffer, clipped to the damaged rectangle** (and to the window's visible region), at the window's place in the back-to-front order; **never directly to the framebuffer**: the compositor stays the only code that copies to the screen (decision 2). Each window's redraw source: **Console** = the `vga_shadow` grid (the cells under the rectangle, drawn by `fbcon_draw_cell` with the window-relative layout); **About** = its static content (the M, the wordmark, the fixed list and footer, set when the window is made); **Calculator** = its engine state (the display string and the keys' states). The pixels are the same as with a surface. Logged once per window: `Desktop: window Console drawn on exposure (its surface, N pages, does not fit the share)`. **Why not refuse to open the window:** a refused Console window would leave the user with no console at all on a large mode with little memory, and the exposure painting is code every window needs anyway (it is how a surface is filled). **Test options:** `desktopnocache` (the cache is never planned) and `desktopnosurface` (no window surface is planned); each `test=desktop…` boot with them must give screens equal, pixel for pixel, to the same scenes without them (section G).

### C5. The toolkit (pure, `kernel/display/ui_*`)

- **Drawing:** rectangles and regions (the damage list), clipping, filled and outlined rounded rectangles (integer quarter-circles), text in Terminus regular and bold (`font.h`), stroke icons by coverage (the coverage code of `wallpaper_core.c`), images (the cached background).
- **Widgets:** label, button (normal, hover, pressed, focused), menu (header, rows, divider), window (title bar, close button, drag, a client surface or exposure painting), dialog.
- **Events:** the mouse is hit-tested from the top down (an open menu or dialog, then the windows by z-order, then the taskbar, then the desktop); a click outside an open menu closes it; during a drag the window keeps the pointer (capture); movement is 1:1 with no acceleration. Keys go to the focused window (the Console window calls `console_handle_key`); with no window focused, any key opens the Console window and is not typed (decision 7); in a menu or dialog, Up, Down, Tab, Enter and Esc. A dialog keeps keys and clicks while it is open. **The Windows key (decision 20)** is taken by the desktop before any window: it toggles the M menu (opened with its first row selected), whether or not a window is focused, and never reaches a window; only an open dialog keeps it.
- **Focus:** a click raises and focuses a window; closing the focused window passes the focus to the next one in z-order; the active window's edge and title colour (Design Guide section 8).
- **Logging (test option `desktoplog`, off by default):** `desktop: …` lines on serial for every menu opened and closed, row chosen, window opened (with its rectangle), raised, dragged to, closed, and every dialog answer; the checks read them with the pixels.

### C6. The clock

`rtc_time.c` decodes the clock read by the existing `cmos_rtc_read()` (the protected `kernel/arch/x86/cmos.c` is not changed). The idle loop reads it once per second (the timer's seconds) and redraws the clock's box only when the minute changes. Every desktop frame marker (`display: frame N`, test options only) also logs the clock string shown (`desktop: clock HH:MM`).

## D. Decision 13: the evidence, and what is not yet proven

**The evidence (1.2, stage 3, the VirtualBox probe of 2026-10-23; local logs, never acceptance evidence):** `build\vbox-probe\` (run 1) and `build\vbox-probe-2\` (the rerun), each with `probe-summary.txt`, `A-case1.serial.log`, `A-case1-before-mouse-ps2m.txt` and `A-case1-after-ps2m.txt`; made by `scripts/vbox-probe.ps1` (added in `a6337fe`, removed in 5a; rerunnable from `287b355`), on the probe ISO `9e7e3498…` (the QEMU side of the same probe ran in Actions run 39889490495). Recorded in [plans/1.2.md](1.2.md), probe result (e), and decision 11.

- **The VM as the probe read it (read only):** VirtualBox 7.2.20 r175154; `hidpointing=usbtablet`, `hidkeyboard=ps2kbd`; **no USB controller enabled** (`usb ohci= ehci= xhci=` all empty).
- **COM `IMouse`:** `AbsoluteSupported=0 RelativeSupported=1 NeedsHostCursor=0`; 4 `PutMouseEvent` calls returned without an error (move 10,−5; left down; up; move −3,7).
- **Before the events,** `info ps2m`: "PS/2 mouse state: normal, stream mode, reporting enabled" (the probe kernel had sent 0xF4 and read its 0xFA).
- **The guest read, by polling the controller, 12 bytes from the aux port, each with status bit 5** (`0x3d`), in both runs: `08 0a 05`, `09 00 00`, `08 00 00`, `38 fd f9`. Decoded as PS/2 3-byte packets: dx +10, dy +5 (PS/2 counts up as positive, so the host's −5, upward); the left button down; the button up; dx −3, dy −7 (both sign bits set: the host's +7, downward). **They are exactly the four calls,** in order, with no other byte.

**How the events reach the guest on `MadireOS-Test` as configured.** The USB tablet has no USB controller to sit on, and the guest has no USB driver, so VirtualBox reports absolute positioning as unsupported; `PutMouseEvent`'s **relative** dx, dy and buttons go to the emulated **PS/2 mouse behind the i8042's aux port**, which turns them into standard 3-byte packets once the guest has enabled reporting. The desktop therefore positions the pointer by relative moves (parked first by a large negative move that the clamp stops at 0,0, as the QEMU sessions do), with no acceleration in the guest.

**Not yet proven on `MadireOS-Test`: delivery through IRQ12.** The probe read the bytes by polling, with IRQ12 off; the stage 11 acceptance showed Madire's driver starting with IRQ12 unmasked but injected no event; the owner's manual check that confirmed IRQ12 (1159 packets) was on `MadireOS-View`, which has a PS/2 mouse, with a local view ISO (not evidence). **Therefore stage 3 adds a report-only proof step** (section E): `MadireOS-Test` (no setting changed; only the ISO attached) boots a test ISO with one extra entry `test=mouse mouselog` around the run's own kernel (packaged on Kali like the module ISO), the script sends the probe's same four `PutMouseEvent` calls, and the report gives the serial log's `mouse: packet 1..4` lines and `Mouse test: done: 4 packets from 12 bytes … IRQ12 delivered N times`. If the four packets do not arrive through IRQ12, decision 13 is raised again before stage 8 (the VirtualBox `desktop` group would then wait, and no VM setting is changed without the owner's approval).

**How the proof step runs (the owner, stage 0):** the laptop is restarted before the VirtualBox step, as usual; host memory is measured as AGENTS.md section 6 says (no application closed without asking the owner); only one VM runs at a time (Kali, which packages the ISO, is powered off before `MadireOS-Test` starts; `MadireOS-View` stays off). **After the proof, `MadireOS-Test`'s resting medium is restored** to the v1.2 release ISO (`build\v1.2-release\madire-os.iso`, SHA-256 `2a2acbe5…`), and the report gives that file's SHA-256 as read after the restore and the VM's attached medium as `VBoxManage showvminfo` reads it.
